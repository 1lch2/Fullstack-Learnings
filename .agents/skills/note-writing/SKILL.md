# 仓库笔记编写

## 使用基线

将 Git 最后提交时间早于 `2025-10-01` 的 `note/**/*.md` 作为格式样本。该样本集共有 119 个已跟踪 Markdown 文件；2026 年笔记以及当前未跟踪笔记不参与风格判断。若目标主题已有邻近笔记，优先遵循同目录和同主题的局部习惯。

## 编写流程

1. 阅读目标文件（若已存在）及同目录下 1 至 3 篇相关笔记，确认标题、命名、链接和措辞习惯。
2. 确定主题边界，先列出概念关系，再按“概念解释 → 示例或实现 → 限制、差异与易错点”的顺序组织内容；简单主题可缩短流程。
3. 使用仓库已有的 Markdown 表达方式与措辞写入内容，保留技术名词、API、命令和代码的原文拼写。
4. 只在确实有帮助时加入表格、图片、引用或外部链接；不要为了套模板强行补齐章节。
5. 完成后检查结构、代码围栏、相对路径和 diff，不要顺手重排无关旧内容。

## 稳定格式

- 将文件放在 `note/<主题目录>/<主题文件名>.md`，文件名遵循所在目录的既有习惯。仓库同时存在 PascalCase、下划线和少量连字符，不能为了统一而批量改名。
- 通常以一个一级标题 `# ...` 开始，标题使用技术名词或“技术名词 - 主题”的简洁形式。正文主要使用 `##` 划分大主题，用 `###` 划分具体概念；不强制固定的章节名称。
- 用中文解释核心概念，保留英文技术术语、类名、函数名和配置键。
- 常用组织顺序是先给定义、用途或问题，再给规则、原理、API 和示例，最后补充限制、对比、性能或易错点（只写与主题相关的部分）。
- 代码使用带语言标识的围栏，例如 ` ```js `、` ```ts `、` ```css `、` ```html `；代码前用一两句说明目的，代码后解释关键行或结果。不同语言的示例分开书写。
- 用行内代码标记 API、变量、命令、文件名、选择器和协议字段；用无序列表列举特性或规则，用有序列表描述流程或步骤。
- 对照关系、字段映射和行为差异适合使用 Markdown 表格；不要把连续段落机械改成表格。
- 对一句话定义、提醒、面试要点或易错点可使用 `>` 引用；引用必须承载信息，不要作为装饰。
- 图片只在能帮助理解布局、流程或可视化结果时使用，优先引用仓库中已有的相对路径资源，例如 `../static/xxx.png`，并检查目标文件确实存在。
- 跨笔记引用使用相对 Markdown 链接，并优先链接到仓库内相关笔记；外部链接只保留可核验且对理解有直接帮助的来源。

## 措辞与行文

以下习惯取自 2021 至 2025 年的历史笔记，优先于 2026 年样本的写法：

- 开头直接给定义、结论或问题，不写“本文介绍”“让我们来看”之类的铺垫；结尾停在最后一个技术点，不写“希望本文对你有帮助”等套话。
- 句子短，通常一句一行；一个段落只推进一个意思，避免把多个独立结论塞进长段。
- 优先使用直述句和仓库常见连接语：“示例如下”“举例如下”“如下”“实际上”“同理”；不使用“众所周知”“显而易见”等空话，也不堆叠“首先/其次/最后/综上所述”的模板。
- 示例后说明结果或现象：代码块内用注释标注关键输出（如 `// 3`）或意图，代码块后用一句话解释运行结果、关键行或限制。
- 用**加粗**标出关键结论、限制和易错点；引用外部原文时在 `>` 引用块内注明来源。
- 对比错误与正确写法时，在代码注释中用 `// ❌` 和 `// ✅` 标记；这些符号只用于代码对比，不在正文中作装饰。
- 概念解释以第三人称为主。历史笔记中的“你/我们”多来自官方文档转述，不作为新笔记的默认写法；也不使用“简单来说”“可以理解为”等口语化表述。
- 术语、API、属性名保持原文拼写，首次出现时可加中文解释；同类术语以同目录既有笔记的写法为准，不强行翻译或统一大小写。
- 未完成或待补充的内容保留 `TODO:`，不用空泛段落填充。

## 内容习惯与边界

- 以可复习、可检索为目标：一个标题聚焦一个主题，先说明“是什么/为什么”，再说明“怎么做/何时不用”，并落到实际应用场景；优先覆盖面试高频考点和易错点。
- 示例应服务于解释，优先使用最小可运行或最小可读片段；涉及多个概念时说明它们之间的关系。
- 技术结论要区分定义、实现细节和经验判断；版本特性、API 签名、浏览器兼容性和具体数值先核实再写，对未经验证的内容标明前提，不把猜测写成规则。
- 笔记若对应 `src/` 下的实现，新增或修改时同步检查代码与笔记是否一致。
- 仅当引用外部资料时，在文末用 `## 参考` 加链接列表；没有外部来源就不加。
- 不默认添加 YAML frontmatter、目录、统一的“总结/参考资料/面试题”尾段或 AI 风格的摘要。历史样本没有这些统一要求。
- 不强制每篇笔记同时包含代码、表格、图片、引用和外链；这些元素在样本中是按主题选择的可选工具。
- 不为了显得完整而堆叠背景、重复同义解释、泛化的“优缺点”或脱离主题的扩展。
- 新建笔记不要复制 2026 年 AI 生成笔记的固定腔调、过度分节、模板化结论或与主题无关的安全提示；如需借鉴内容，先将其事实与示例独立核验。
- 修改旧笔记时保留已有的术语、链接、图片引用和章节组织；只调整与请求直接相关的内容，避免全篇格式化。

## 完成检查

- [ ] 文件路径和文件名符合目标目录的既有习惯。
- [ ] 有清晰的一级标题，标题层级没有跳跃或无意义的细分。
- [ ] 开头直接进入主题，示例后说明结果，没有模板化铺垫或套话收尾。
- [ ] 措辞与同目录历史笔记一致（短句、一句一行、术语写法）；引用外部资料已注明来源。
- [ ] 定义、核心规则和示例之间的关系清楚；没有为凑格式而添加可选元素。
- [ ] 每个代码围栏带正确语言标识，围栏成对，示例中的关键结果或限制已说明。
- [ ] 表格列对齐且只用于对照；图片和仓库内链接的相对路径可解析。
- [ ] 没有误用 2026 年样本的 AI 模板化结构，没有凭空补充未经核验的结论。
- [ ] 编辑任务只改动请求范围；运行 `git diff --check`，并检查 `git diff -- note/` 是否存在无关改动。
